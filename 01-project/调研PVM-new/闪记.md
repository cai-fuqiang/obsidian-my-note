> >  Unfortunately, current hardware (e.g., Intel VT-x [ 40] and AMD-V [47 ]) only has a single level of architectural support for virtualization. As a result, implementing nested virtualization requires complex and costly software efforts, especially in the 𝐿0 hypervisor

> [!PDF|important] [[sosp2023-pvm-paper.pdf#page=3&selection=105,12,109,10&color=important|📖 Section 2 主题: 嵌套虚拟化的开销来源]]
> > In this section, we compare 2-level nested virtualization with traditional single-level virtualization (based on Intel VT-x) and identify the primary sources of overhead in nested virtualization.

> 这是本章的重点，也是我比较关心的内容，即嵌套虚拟化相比 single-level 虚拟化的开销来源

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=3&selection=251,0,251,4&color=yellow|📖 嵌套虚拟化的主要开销来源]]
> 
> 开销的原因只有一个:  ==[[sosp2023-pvm-paper.pdf#page=3&selection=251,26,252,59&color=note|MANY MANY world switch]] ==: 
> * [[sosp2023-pvm-paper.pdf#page=3&selection=257,2,267,16|L2 switch to L0 ]], L2 的 特权指令首先被L0 捕获 L0 捕获后，其主要是将该trap注入到L1，让L1处理, 
> * [[sosp2023-pvm-paper.pdf#page=3&selection=288,4,292,1|L0 switch to L1]]: L0做完准备后， 通过 VM entry 切换到L1, L1 处理"VM-exit" -- 来自于 L2 的 Trap(其实是L0注入的)
> * [[sosp2023-pvm-paper.pdf#page=3&selection=300,0,309,30|L1 switch to L0]] : L1 做完模拟后，调用 vmresume 切换到L2，恢复虚拟机运行。但是在L1 中 vmresume 是特权指令，执行该指令会trap到L0
> * [[sosp2023-pvm-paper.pdf#page=3&selection=309,31,326,1|L0 switch L2]] : L0 接收到来自L1 的 vmresume trap, 在VMX root operation 中执行 vmresume 恢复L2 执行
> 所以, 由于L1<->L2 不存在纯硬件的world switch，其需要借助L0 模拟。从上面列举的信息看，似乎是产生了 [[sosp2023-pvm-paper.pdf#page=3&selection=342,2,342,39|两倍的world switch]] 
> ```ad-question
> 但是真的是两倍损耗么?
> 远远不是! 因为在L1 emulate 的过程中, 可能会因执行特权指令多次产生vm exit。例如下面提到的 `VMREAD/VMWRITE`
> ```

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=4&selection=28,0,28,3&color=yellow|📖|目前减少嵌套虚拟化过程中的world switch措施]]
> 首先说结论，VMX 硬件层面引入 `shadow VMCS` 让 L1中执行 `VMREAD/VMWRITE`不在VM exit
> 为了更好的介绍这部分内容，我们先简单介绍下在嵌套虚拟化中 VMCS的种类:
> 
> * VMCS<sub>01</sub>: L0<-> L1
> * VMCS<sub>02</sub>: L0<->L2
> * VMCS<sub>12</sub>: L1, L2 之前无法通过硬件切换，所以这个结构就是一个"假的", 仅仅用作shadow VMCS features使用，L1执行 VMREAD/VMWRITE 不会vmexit to L0,而是直接读/写 这个假的"VMCS"
>  **所以vmcs shadow 作用仅仅是==避免了L1 执行 `VMREAD/VMWRITE` 造成的vm-exit==，并没有解决==L1<->L2的world switch 完全由L0模拟==, 所以并没有从根本上解决问题**
>  但是提升仍然很大，  [[sosp2023-pvm-paper.pdf#page=4&selection=91,0,106,1|L1 在emulate L2 VM exit时，大约会有40-50次的VMREAD/VMWRITE]]
>  
> ```ad-important
> 关于为什么要区分 VMCS<sub>01</sub>, VMCS<sub>02</sub>, VMCS<sub>12</sub>, 而不是用一个或者用其中两个，这里不讨论。可以参考 [[Ben-Yehuda-nested-virt.pdf]]
> ```
>

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=4&selection=217,0,219,21&color=yellow|📖 嵌套虚拟化中内存虚拟化实现概述]]
> 首先,  一共有[[sosp2023-pvm-paper.pdf#page=4&selection=259,0,262,24| 三级页表]]
> * GVA<sub>L2</sub>->GPA<sub>L2</sub>: L2 维护
> * GPA<sub>L2</sub>->GPA<sub>L1</sub>: L1 维护
> * GPA<sub>L1</sub>->HPA <sub>L0</sub>:L0维护
> 其实现的**本质上，还是使用EPT 进行加速，但是 [[sosp2023-pvm-paper.pdf#page=4&selection=332,7,333,24|EPT不支持嵌套虚拟化]] , 所以 ==需要L0完成== 前面两级页表==在L0的虚拟化==，跟影子页表类似，也就是==通过一级页表完成 GVA<sub>L2</sub>-> GPA<sub>L1</sub>==**
> 
> 而根据L1 的内存虚拟化的实现，嵌套虚拟化有两种实现方式:
> * L0 使用 EPT, L1 使用 SPT(影子页表) - **SPT-on-EPT**
>    + 使用 SPT<sub>12</sub>  + EPT<sub>01</sub> [[sosp2023-pvm-paper.pdf#page=4&selection=372,2,383,4|出处]]
>    + 即便是使用了EPT，但是开销还是很大: [[sosp2023-pvm-paper.pdf#page=4&selection=399,8,428,51|开销来自于需要处理guest的每一个#PF, 然而这个行为造成的影响在嵌套虚拟化会加剧，因为L2 首先会trap 到 L0, 然后在转发到L1]]

>    + 使用 GPT<sub>2</sub> + EPT<sub>02</sub>

> 2. 更新L1 的 GPT1(GVA1->GPA1 主要是给QEMU用，可以不关心) 和 SPT12
