# 进一步分析

## 查看是否有未响应的cpu
通过:
```
[188432.543959] Sending IPI to other cpus...
[188442.552090] Starting crashdump kernel...
```

这两行看, 中间经过10s， 代码为:
```sh
machine_crash_shutdown
=> crashing_cpu = smp_processor_id();
# 保存当前cpu pt_regs
=> crash_save_cpu(regs, crashing_cpu);
=> crash_smp_send_stop();
   => ncpus = num_online_cpus() - 1;
   => smp_call_function(crash_shutdown_secondary, NULL, 0);
   # 总的等待时间为10s
   => timeout = MSEC_PER_SEC * 10;
   => pr_emerg("Sending IPI to other cpus...\n");
   => while ((cpumask_weight(&cpus_in_crash) < ncpus) && timeout--) {
		  mdelay(1);
		  cpu_relax();
=> cpumask_set_cpu(crashing_cpu, &cpus_in_crash);
=> pr_info("Starting crashdump kernel...\n");
```

而`machine_crash_shutdown`发送 ipi后，等待的超超时时间为10s，说明有一些cpu一直没有相应。这些cpu还在跑。。。而未响应的cpu可以再`cpus_in_crash`查看

## machine_kexec获取的pt_regs是否应该包含machine_kexec堆栈
```
no_context
=> pr_alert("CPU %d Unable to handle kernel paging request at "
	  "virtual address %0*lx, era == %0*lx, ra == %0*lx\n",
   => die("Oops", regs);
      => if (regs && kexec_should_crash(current)) 
         => crash_kexec(regs);

crash_kexec
  __crash_kexec
    machine_crash_shutdown
      crashing_cpu = smp_processor_id();
        crash_save_cpu(regs, crashing_cpu);
```
可以发现通过上面路径获取的`pt_regs` 不应该包含machine_kexec的堆栈，仅包含触发`#PF`的堆栈。
