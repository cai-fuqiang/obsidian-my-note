# 2. Background and Motivation

> [!PDF|important] [[sosp2023-pvm-paper.pdf#page=3&selection=90,27,105,10&color=important|📖当前嵌套虚拟化现状]]
> >  Unfortunately, current hardware (e.g., Intel VT-x [ 40] and AMD-V [47 ]) only has a single level of architectural support for virtualization. As a result, implementing nested virtualization requires complex and costly software efforts, especially in the 𝐿0 hypervisor
> 
> hardware 不支持嵌套虚拟化，软件做了复杂的模拟。尤其是在L0

> [!PDF|important] [[sosp2023-pvm-paper.pdf#page=3&selection=105,12,109,10&color=important|📖 Section 2 主题: 嵌套虚拟化的开销来源]]
> > In this section, we compare 2-level nested virtualization with traditional single-level virtualization (based on Intel VT-x) and identify the primary sources of overhead in nested virtualization.
> 
> 这是本章的重点，也是我比较关心的内容，即嵌套虚拟化相比 single-level 虚拟化的开销来源

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=3&selection=251,0,251,4&color=yellow|📖 嵌套虚拟化的主要开销来源]]
> 
> 开销的原因只有一个:  ==[[sosp2023-pvm-paper.pdf#page=3&selection=251,26,252,59&color=note|MANY MANY world switch]] ==: 
> * [[sosp2023-pvm-paper.pdf#page=3&selection=257,2,267,16|L2 switch to L0 ]], L2 的 特权指令首先被L0 捕获 L0 捕获后，其主要是将该trap注入到L1，让L1处理, 
> * [[sosp2023-pvm-paper.pdf#page=3&selection=288,4,292,1|L0 switch to L1]]: L0做完准备后， 通过 VM entry 切换到L1, L1 处理"VM-exit" -- 来自于 L2 的 Trap(其实是L0注入的)
> * [[sosp2023-pvm-paper.pdf#page=3&selection=300,0,309,30|L1 switch to L0]] : L1 做完模拟后，调用 vmresume 切换到L2，恢复虚拟机运行。但是在L1 中 vmresume 是特权指令，执行该指令会trap到L0
> * [[sosp2023-pvm-paper.pdf#page=3&selection=309,31,326,1|L0 switch L2]] : L0 接收到来自L1 的 vmresume trap, 在VMX root operation 中执行 vmresume 恢复L2 执行
> 所以, 由于L1<->L2 不存在纯硬件的world switch，其需要借助L0 模拟。从上面列举的信息看，似乎是产生了 [[sosp2023-pvm-paper.pdf#page=3&selection=342,2,342,39|两倍的world switch]] 
> ```ad-question
> 但是真的是两倍损耗么?
> 远远不是! 因为在L1 emulate 的过程中, 可能会因执行特权指令多次产生vm exit。例如下面提到的 `VMREAD/VMWRITE`
> ```

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=4&selection=28,0,28,3&color=yellow|📖|目前减少嵌套虚拟化过程中的world switch措施]]
> 首先说结论，VMX 硬件层面引入 `shadow VMCS` 让 L1中执行 `VMREAD/VMWRITE`不在VM exit
> 为了更好的介绍这部分内容，我们先简单介绍下在嵌套虚拟化中 VMCS的种类:
> 
> * VMCS<sub>01</sub>: L0<-> L1
> * VMCS<sub>02</sub>: L0<->L2
> * VMCS<sub>12</sub>: L1, L2 之前无法通过硬件切换，所以这个结构就是一个"假的", 仅仅用作shadow VMCS features使用，L1执行 VMREAD/VMWRITE 不会vmexit to L0,而是直接读/写 这个假的"VMCS"
>  **所以vmcs shadow 作用仅仅是==避免了L1 执行 `VMREAD/VMWRITE` 造成的vm-exit==，并没有解决==L1<->L2的world switch 完全由L0模拟==, 所以并没有从根本上解决问题**
>  但是提升仍然很大，  [[sosp2023-pvm-paper.pdf#page=4&selection=91,0,106,1|L1 在emulate L2 VM exit时，大约会有40-50次的VMREAD/VMWRITE]]
>  
> ```ad-important
> 关于为什么要区分 VMCS<sub>01</sub>, VMCS<sub>02</sub>, VMCS<sub>12</sub>, 而不是用一个或者用其中两个，这里不讨论。可以参考 [[Ben-Yehuda-nested-virt.pdf]]
> ```

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=4&selection=217,0,219,21&color=yellow|📖 嵌套虚拟化中内存虚拟化实现概述]]
> 首先,  一共有[[sosp2023-pvm-paper.pdf#page=4&selection=259,0,262,24| 三级页表]]
> * GVA<sub>L2</sub>->GPA<sub>L2</sub>: L2 维护

> 其实现的**本质上，还是使用EPT 进行加速，但是 [[sosp2023-pvm-paper.pdf#page=4&selection=332,7,333,24|EPT不支持嵌套虚拟化]] , 所以 ==需要L0完成== 前面两级页表==在L0的虚拟化==，跟影子页表类似，也就是==通过一级页表完成 GVA<sub>L2</sub>-> GPA<sub>L1</sub>==**
> 
> 而根据L1 的内存虚拟化的实现，嵌套虚拟化有两种实现方式:
> * L0 使用 EPT, L1 使用 SPT(影子页表) - **SPT-on-EPT**
>    + 使用 SPT<sub>12</sub>  + EPT<sub>01</sub> [[sosp2023-pvm-paper.pdf#page=4&selection=372,2,383,4|出处]]
>    + 即便是使用了EPT，但是开销还是很大: [[sosp2023-pvm-paper.pdf#page=4&selection=399,8,428,51|开销来自于需要处理guest的每一个#PF, 然而这个行为造成的影响在嵌套虚拟化会加剧，因为L2 首先会trap 到 L0, 然后在转发到L1]]
> * L0 使用 EPT, L1 使用 EPT - **EPT-on-EPT**
>    + 使用 GPT<sub>2</sub> + EPT<sub>02</sub>

> [!PDF|note] [[sosp2023-pvm-paper.pdf#page=4&selection=438,7,438,40&color=note|📖]]
> >  two phases of page table updates
> 
>  主要分为两个阶段
>  
> 1. 首先建立L2 GPT2
> 2. 更新L1 的 GPT1(GVA1->GPA1 主要是给QEMU用，可以不关心) 和 SPT12

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=4&selection=448,16,453,7&color=yellow|📖建立GPT阶段触发#PF处理流程]]
> > More specifically, in the first phase, an access to an absent GVA𝐿2 in GPT2
> 
> 在第一个阶段由于 L2 GPT还未建立完全, L2访问GVA<sub>L2</sub>触发缺页,  该缺页最终需要 `hypervisor` 将 PF的结果 "原样"(其实也就是CR2即触发PF的虚拟地址) 转发到L2, 然而这个流程在nested virtualization中特别费劲
> 1. GPT2 trigger L2 pagefault 并且切换到L0 (➀)
> 2. L0 通过写 VMCS<sub>01</sub> 将 该 PF注入到 L1(➁), 并且切换到L1(➂)
> 3. L1 收到了这是L2 page fault 通过写VMCS<sub>12</sub> 将 PF 预转发到L1(➃) , 并且恢复L2执行.但是恢复L2执行类似于vmresume指令，会先trap到L0(➄)
> 4. L0 在VMCS<sub>12</sub>中发现了PF 注入请求，并将其写入VMCS<sub>02</sub>(➆)
> 5. L0 使用 VMCS<sub>02</sub>恢复L2(➆).
> 6. L2 page fault handler 使用这个刚刚建立映射的新page 建立GVA<sub>L2</sub>->GPA<sub>L2</sub>的映射(➇)
> 7. L2 kernel 返回用户态(➈)
> 
> 整个过程涉及world switch 次数
> * L2->L0(1)
> * L1->L0(1)
> * L0->L1(2)
> 
> 共四次

> [!PDF|note] [[sosp2023-pvm-paper.pdf#page=4&selection=564,33,567,1&color=note|📖 GPT2 READ only 的原因以及实现方法简述]]
> >  since GPT2 is read-only,
> 
> 根据GPT2 的映射关系(GVA<sub>L2</sub>->GPA<sub>L2</sub>, 建立shadow pagetable,而SPT 是 GPA<sub>L2</sub>->GPA<sub>L1</sub>的映射。而GPA<sub>L2</sub>和GPA<sub>L1</sub> 又是固定的映射关系（假设L1 将L2的内存pin住). 所以GPT映射关系改变，必将引起SPT映射关系改变
> 
> 如何捕获GPT的改变呢？将GPT所在的影子页表都修改为wp. 这样每次write WP的page 都会Trap到L0
> ```ad-question
> 怎么能知道这个PAGE是GPT呢? [[How to identify GPT in SPT]]
> ```

> [!PDF|note] [[sosp2023-pvm-paper.pdf#page=5&selection=324,0,351,32&color=note|📖 SPT readonly使world switch 次数更多]]
> > every update to GPT2 needs assistance from 𝐿1. Hence, step ➇ could further cause multiple rounds of switches between 𝐿2 and 𝐿1 via 𝐿0 (not illustrated in Figure 3(a)), depending on the number of page table levels.
> 
> 因为GPT2 是READ-ONLY的，也就是说。L2 page fault handler 每次因缺页更新每一级GPT都会触发多轮次的 前面提到的一阶段流程。这个多轮次的中的轮次和多种因素有关:
> * Numbers of Guest Page Table level
> * Only Need update missing level . 越靠前的page table level 覆盖的address range越大。可能之前的PF 已经在前面的level中填充好了 相应的entry，本次PF L2 kernel 会考虑直接使用该entry，而不modify，所以只需填充(write) 后面几级not present（甚至最后一级）的 page table entry.

> [!PDF|note] [[sosp2023-pvm-paper.pdf#page=5&selection=352,36,376,14&color=note|📖|最坏情况下 L2 PF world switch 次数]]
> > In the first phase, 𝐿0 can be involved up to 2𝑛 + 2 times with 4𝑛 + 4 world switches
> 
> $4n+4 = 4(n+1)$
> * $n$表示页面的level number
> * $4$表示每次触发`#PF`要触发4次world switch
> * $1$表示 L2 userspace 触发 `#PF`, hypervisor 转发到 L2
> ```ad-question
>  但是似乎，这个结论并不准确，举个例子, 当guest 触发`#PF`时, 该 GPA 在GPT的4-level page table中, 只有前两级有映射, 此时 3th GPT 中关于该GPA的 page table entry 为 not present, 此时，L2 PF handler 分配一个page, 作为 4th GPT。而此时 L1并不能识别到这个page 是 GPT, 当 L2 PF handler又分配了一个PAGE作为最终的GVA的GPA所在的页。并填充 4th GPT时，GPT 并不是WP。所以，并不能达到文章中所提到的 $4n+4$
> ```

> [!PDF|note] [[sosp2023-pvm-paper.pdf#page=5&selection=387,0,401,37&color=note|第二阶段必然产生PF的原因]]
> > The following access to GPA𝐿2 , which was added to GPT2 during the first phase, triggers a page fault in 𝐿1 since GPA𝐿2 is absent from GPT1 and hence SPT12. 
> 
> 只要是Guest 对GPT2 page table entry 做了write操作。如果写入的page table entry是:
> *  **not present**:  说明之前GPT中没有映射. 那么SPT中也没有。所以必然会产生`#PF`
> * **have old value**: 当Guest<sub>L2</sub> 写GPT2时，会因为PF trap 到 L1, L1会处理下该page table entry所映射的地址范围的SPT, 简单的方法是全部invalidate。(全部修改为not present)。那后续的GVA<sub>L2</sub>的访问也会产生 `#PF`

> [!PDF|yellow] [[sosp2023-pvm-paper.pdf#page=5&selection=414,31,449,1&color=yellow|📖 二阶段和一阶段的不同点]]
> > First, at step ➍ the 𝐿1 kernel handles the page fault and updates SPT12. Second, step ➐ returns directly to 𝐿2 user space without involving the 𝐿2 guest kernel. In the second phase, there are four more world switches, including trapping to 𝐿0 twice.

> ```ad-faq
> Q: 和谁很像呢？
> A: **kernel context switch**
> kernel 在切换进程时，涉及两个地址空间的切换。kernel context switch 其实就是一个switcher，其需要在两个地址空间中拥有相同的地址
> ```
