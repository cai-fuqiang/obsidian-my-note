# background
JANUS仍然是在安全容器使用云底座背景下，为解决嵌套虚拟化性能而诞生的。其主要是为了降低`PVM`因影子页表而带来的针对某些场景的性能损耗。

具体来说，目前有两种内存虚拟化的实现:

![[JANUS文献笔记汇总#^db6eb9]]

两种嵌套内存虚拟化的实现各有优劣:

| 实现方式    | 代表者     | 优点                      | 缺点                                                                    | 适合场景         |
| ------- | ------- | ----------------------- | --------------------------------------------------------------------- | ------------ |
| SPT+EPT | PVM     | GPT fault 无需L0参与        | CR3 加载的是shadow root pgtable，如果GVA->GPA映射关系可能经常改变，从而触发更多的`#PF`, 比较依赖场景 | 冷内存场景，例如内核启动 |
| GPT+EPT | NEST VM | 映射关系固定，`#PF` 直接由guest处理 | 建立 EPT页表需要L0参与，代价更高                                                   | 热内存场景        |
如下:
![[JANUS文献笔记汇总#^ea569b]]

另外, 这也反映了两种虚拟化在不同的主导方所产生的优势不同:

| 虚拟化方式    | 主导方 | 优点                          |
| -------- | --- | --------------------------- |
| PVM      | L1  | world switch fast           |
| NEST KVM | L0  | EPT02 create a STABLE map.. |
也就是说，由L1 主导的`PVM`, 由于其event handle bypassL0直接trap L1，更适合处理world switch。
由L0 主导的 `NEST KVM`，更适合建立较稳定的映射，从而减少 因映射改变而造成`#PF`。

> [!notion] 能不能将两者结合？

即使用`PVM` 的在 `L1` 以半虚拟化的方式，处理 VM(L2)和hypervisor 之间的world switch。又能让 `L0` 以`GPT+EPT02`
