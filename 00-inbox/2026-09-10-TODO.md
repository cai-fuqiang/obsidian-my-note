# mmu_zap_unsync_children

```cpp
struct mmu_page_path {
	struct kvm_mmu_page *parent[PT64_ROOT_MAX_LEVEL];
	unsigned int idx[PT64_ROOT_MAX_LEVEL];
};
```

`mmu_page_path` 用于记录 `unsync sp`以及其`parent` 的链。其作用是方便后续流程对`unsync sp`做操作后(change to sync sp or release unsync sp) 。置位`parent sp`的 `unsync_bitmap`

# kvm_mmu_pages

```cpp
struct kvm_mmu_pages {
	struct mmu_page_and_offset {
		struct kvm_mmu_page *sp;
		unsigned int idx;
	} page[KVM_PAGE_ARRAY_NR];
	unsigned int nr;
};
```

`kvm_mmu_pages` 包含了一个数组，该数组记录 一个sp 和一个index，sp其实表示 `unsync_sp` 或者`unsync_parent sp`(也就是unsync sp的parent或者祖宗)。而index则表示其在parent spt 或者`unsync_child_bitmap`中的index。

> [!note] idx有一个特殊值: `INVALID_INDEX`, 常用作顶层的 `unsync parent sp`， `for_each_sp`要求 `pvec->page[0].idx`必须为该值。为什么要这样做呢？**因为idx标记着该sp在parent sp中的index，而==顶层==的sp==没有parent==。**
> ```
> mmu_pages_first
> => WARN_ON_ONCE(pvec->page[0].idx != INVALID_INDEX);
> ```

# mmu_unsync_walk

`mmu_unsync_walk` 作用是遍历 sp tree，找到所有`unsync`的`sp`, 以及其parent link, 以[[kvm_mmu_pages_example.excalidraw|特定的格式]], 存储到 `kvm_mmu_pages`中。

> [!note] 该过程只是find。并不会 `clear_unsync_child_bit()`。
> > [!missing] 除非在遍历过程中发现，某个sp均没有 unsync child sp了。
> 
>> [!todo] 这里需要关注下，这个流程会不会有race。

## for_each_sp

`for_each_sp`的作用是, 遍历`mmu_unsync_walk` 中保存的`kvm_mmu_pages` 数组。获取每一个 `unsync sp chain`,  将这些信息存放到 `mmu_page_path`进入循环体。整个的循环流程由 `mmu_pages_first` , `mmu_pages_next` 控制。

循环体中往往会将unsync page 释放或者变为sync，最终清除parent sp 的 unsync bitmap。

## kvm_mmu_page_unlink_children

其作用是将该sp 的所有child sp 全部解映射。last level 也全部`drop_spte`。而解映射后，在一定的条件下会将这些解映射的sp zap具体条件:
```
mmu_page_zap_pte
=> if (is_shadow_present_pte(pte))
   \> if (is_last_spte(pte, sp->role.level))
      \> drop_spte
\> else
   \> if (tdp_enable && invalid_list && child->role.guest_mode
       && !child->parent_ptes.val)
       \> kvm_mmu_prepare_zap_page(kvm, child, invalid_list)
```

* `tdp_enable`+ `child->role.guest_mode`: 详见 [[https://github.com/torvalds/linux/commit/2de4085ccceaf075f7c8d1688338fb82e2349f0f|upstream commit|]], 主要的观点是，在嵌套虚拟化场景下，回收影子页时，只会回收`unsync`的 shadow page，但是不会回收sync的。当运行大量嵌套虚拟化虚机时，随着时间推移，会留下很多`unlink`的页面。这些页面直到达到影子页表上限才开始回收。另外可能因为影子页表堆积造成 rmap和 page hash map 臃肿，而造成性能损失。

  所以，在嵌套虚拟化场景下，会直接回收child sp
  > [!note] `child->role.guest_mode` 
  
  *  `!child->parent_ptes.val`： 表示没有别的parent shadow page 指向改sp了，可以安全释放。
