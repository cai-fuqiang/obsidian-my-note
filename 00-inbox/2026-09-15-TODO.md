# 随笔记录
使用影子页表的 vCPU 在使用mmu , 进行访问时, 会经过以下副本链:
```
tlb -> spt -> gpt
```

也就是说，硬件会使用 `tlb` 进行地址转换，如果`tlb` 不存在，则会从`walk spt` 来创造`tlb`,  而spt 和gpt之间有个固定的映射关系。

如果修改了`gpt` 则意味着 `spt` 也需要作变更，这时，我们需要track gpt write，即通过写保护的方式将这些gpt保护起来，只要有人写，就会触发`#PF(wp)`, 在 `hyper`中将 sync spt。

而我们在`zap va range` 等操作时，往往会clear 很多va的所在的 `pte`, 然后在执行`tlb flush`(branch tlb flush， 为了减少tlb shootdown的成本)。所以我们可以不track gpte write，而是在最后的`tlb flush` 时，再sync pte。

于是, tlb flush 兼顾着两方面责任:
*  flush CPU hardware tlb
* sync (invalid) spte

ok，也就是说，在该cpu tlb flush后，看到的一定是，sync 的spte。

***

如何做到呢?

以guest 中，执行 `invlpg` 指令为例:
```
handle_invlpg
=> kvm_mmu_invalidate_addr
   => __kvm_mmu_invalidate_addr(,,addr, mmu->root.hpa and mmu->prev_roots[])
```

如果说`mmu->root.hpa` 指向的spt tree 是 tlb 的backend，而和 `mmu->prev_roots[]`, 就相当于带 pcid feature 的tlb backend, 本质上都是cpu 可能使用的副本。而这里并没有判断，这个va是属于哪个root的。所以在这里都更新下。其会尝试flush 该cpu 所有root的 tlb.

而`__kvm_mmu_invalidate_addr` 需要保证 `va` 所使用的 整个的 `spt link` 都是`sync`的, 这样才会得到正确的映射关系。所以该函数会遍历整个link，找到不同步的`spt`, 然后`sync`

> [!question] 除了 `last level spt`  其他的page table也会有不`sync`的么, 答案是的。因为`non-last level spt` 可能因为write flood 而将spt 置为 `unsync`.

```cpp
__kvm_mmu_invalidate_addr
=> write_lock(&vcpu->kvm->mmu_lock);
=> for_each_shadow_entry_using_root(vcpu, root_hpa, addr, iterator)
   => int ret = kvm_sync_spte(vcpu, sp, iterator.index);
      => vcpu->arch.mmu->sync_spte()
   => if (ret < 0)
	  \> mmu_page_zap_pte(vcpu->kvm, sp, iterator.sptep, NULL);
   => if (ret)
      \> kvm_flush_remote_tlbs_sptep(vcpu->kvm, iterator.sptep);
```

而 `FNAME(sync_spte)`代码:
```cpp
FNAME(sync_spte)
# 得到要sync spte 的gpa
=> pte_gpa = first_pte_gpa + i * sizeof(pt_element_t);
# 获取 gpte的值
=> kvm_vcpu_read_guest_atomic(vcpu, pte_gpa, &gpte,
				       sizeof(pt_element_t))
# 这个可以先不看，相当于prefetch invalid, 可以加速整个spt的sync 
=> FNAME(prefetch_invalid_gpte)(vcpu, sp, &sp->spt[i], gpte)

# 获取gfn 和 pte_access, 并判断在当前gpte_acess下是否需要 wp。举一个例子，如果dirty bit
# 没有set，则需要wp来track page write
=> 	gfn = gpte_to_gfn(gpte);
	pte_access = sp->role.access;
	pte_access &= FNAME(gpte_access)(gpte);
	FNAME(protect_clean_gpte)(vcpu->arch.mmu->w, &pte_access, gpte);
# 如果 新的 pte 不是present，或者gfn 发生了更改，那这里直接drop_spte. 解除映射关系
=> 	if ((pte_access | shadow_present_mask) == SHADOW_NONPRESENT_VALUE ||
	    gfn != kvm_mmu_page_get_gfn(sp, i)) {
		drop_spte(vcpu->kvm, &sp->spt[i]);
		return 1;
	}
# 剩下的就是 access right 发生 了改变，如果没有发生改变，则直接return. 注意这里不是直接
# 比较spte和gpte，而是通过 sp->shadowed_translation 中获取。因为host 也会根据自己的
# 内存管理需求，置位 acecss bit
=> if (kvm_mmu_page_get_access(sp, i) == pte_access)
   => return 0
   
# 更新 sp->shadowed_translation 中的 access
=> kvm_mmu_page_set_access(sp, i, pte_access);
=> sptep = &sp->spt[i]
=> spte = *sptep
=> host_writable = spte & shadow_host_writable_mask;
# 根据多方需求，制作spte
=> make_spte(vcpu, sp, slot, pte_access, gfn,
		  spte_to_pfn(spte), spte, true, true,
		  host_writable, &spte);

# 更新 spte
=> mmu_spte_update(sptep, spte)
```

ok，执行该函数后，如果仅仅是`access right` 不同， 直接执行`mmu_spte_update()` 更新spte，否则执行`drop_spte()` 将映射关系解除。

> [!note] 注意，该流程并不会 将`unsync sp-> sync`

***

另外，还有一个分支可能会用到 sync 流程。但是和该流程完全不同是，其会把 `unsync sp-> sync` :
```cpp
mmu_sync_children
=> while (mmu_unsync_walk())
   \> for_each_sp(pages, sp, parents, i)
      \> protected |= kvm_vcpu_write_protect_gfn(vcpu, sp->gfn);
=> for_each_sp(pages, sp, parents, i)
   # 将 sp 置为 sync
   => kvm_unlink_unsync_page(vcpu->kvm, sp);
      => sp->unsync = 0
   # sync page
   => flush |= kvm_sync_page(vcpu, sp, &invalid_list) > 0;
   => mmu_pages_clear_parents(&parents);
```

步骤大致如下:
1. 将sp置为 wp
2. sp->unsync = 0
3. sync gpt->spt

最终，在 `kvm_sync_page()->make_spte()` 时，难到不会把last level sp 再变为 `unsync`么?
```cpp
make_spte
=> if (pte_access & ACC_WRITE_MASK) {
		if ((!is_last_spte(old_spte, level) || !is_writable_pte(old_spte)) &&
		    mmu_try_to_unsync_pages(vcpu->kvm,
		        slot, gfn, synchronizing, prefetch))
			wrprot = true;
   }
```
